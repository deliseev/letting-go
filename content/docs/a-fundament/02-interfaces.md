В Python интерфейс — это обещание, которое класс даёт заранее.
`class FileStorage(Storage)` объявляет намерение до того, как
написан первый метод, и `abc.ABC` следит, чтобы обещание было
выполнено.

В Go обещаний нет. Тип реализует интерфейс, если у него есть нужные
методы, — и никогда об этом не узнаёт. Соответствие проверяется в
точке использования, а не в точке объявления.

Из этой перестановки следует почти всё остальное в модуле, включая
то, что интерфейсы теперь принято объявлять не там, где вы привыкли.

## Контракт не там, где его написали

Первый рефлекс переносится целиком: сущность есть — значит, нужен
контракт.

```go
type Storer interface {
	Save(c Course) error
	Load(id int) (Course, error)
	Delete(id int) error
	List() ([]Course, error)
}

type postgresStore struct{ db *sql.DB }

func (s *postgresStore) Save(c Course) error { ... }
```

Компилятор доволен, `go vet` молчит, ошибки нет. Проблема
проявится позже — когда понадобится второй пакет, которому нужен
только `Load`, и он всё равно потащит за собой все четыре метода.

Идиома переворачивает направление. Интерфейс объявляет **тот, кто
им пользуется**, под свою нужду:

```go
package report

type courseLoader interface {
	Load(id int) (Course, error)
}

func Render(l courseLoader, id int) ([]byte, error) { ... }
```

Пакет `report` не знает про `postgresStore`, не импортирует его и
не требует от него ничего сверх одного метода. Пакет с хранилищем
не знает про `report`. Связи между ними нет вообще — она возникает
в момент вызова и там же исчезает.

Отсюда правило, которое стоит запомнить дословно: **принимай
интерфейсы, возвращай структуры**.

## Толстый контракт

Прямое следствие первой привычки — интерфейс, повторяющий все
методы типа. В Python это выглядит естественно: абстрактный класс
описывает сущность целиком.

В Go размер интерфейса — это цена. Каждый метод в контракте
сокращает число типов, которые ему удовлетворяют, и увеличивает
число мест, которые придётся править при изменении.

```go
type Notifier interface {
	Notify(s Student, msg string) error
}
```

Один метод. Ему удовлетворяет и почтовая отправка, и запись в лог,
и мок в тесте на три строки — без всякой фабрики и без библиотеки
моков.

Эталон масштаба — `io.Writer`: один метод, и на нём держится
половина стандартной библиотеки. Если ваш интерфейс больше трёх
методов, скорее всего он описывает тип, а не потребность.

Ошибку несоответствия ловит место вызова. Пусть у хранилища метод
называется `Get`, а не `Load`:

```go
s := NewStore(db)
data, err := report.Render(s, 42)
```

```text
./report.go:22:12: cannot use s (variable of type *postgresStore)
as courseLoader value in argument to Render: *postgresStore does
not implement courseLoader (missing method Load)
```

## Конструктор, который прячет тип

Привычка «программируй против абстракции» даёт вот такое:

```go
func NewStore(db *sql.DB) Storer {
	return &postgresStore{db: db}
}
```

Возвращается интерфейс. Всё, что не входит в `Storer`, снаружи
недоступно — включая `Close`, который у типа есть:

```go
func main() {
	s := NewStore(db)
	defer s.Close()
}
```

```text
./main.go:18:4: s.Close undefined (type Storer has no field or
method Close)
```

Обратите внимание на позицию: ошибка указывает на `defer s.Close()`,
а причина — в сигнатуре `NewStore`, страницей выше.
Место ошибки и место причины в Go расходятся регулярно, и умение
не искать проблему там, куда показывает компилятор, экономит
больше времени, чем любое знание синтаксиса.

Идиома — возвращать конкретный тип:

```go
func NewStore(db *sql.DB) *postgresStore {
	return &postgresStore{db: db}
}
```

Вызывающий сам решит, какой минимальный контракт ему нужен. Ничего
не потеряно: структуру всегда можно передать туда, где ждут
интерфейс, а обратно — нет.

## nil, который не nil

Самая дорогая ловушка модуля не даёт ни ошибки компиляции, ни
предупреждения.

```go
type ValidationError struct{ Field string }

func (e *ValidationError) Error() string { ... }

func validate(c Course) error {
	var e *ValidationError
	if c.title == "" {
		e = &ValidationError{Field: "title"}
	}
	return e
}
```

```go
if err := validate(c); err != nil {
	fmt.Println("ошибка:", err)
}
```

Для корректного курса печатается `ошибка: <nil>`.

Интерфейс в Go — это пара: тип и значение. `err != nil` истинно,
если непусто **хотя бы одно** из двух. Возвращая nil-указатель
конкретного типа, вы кладёте в интерфейс пару `(*ValidationError,
nil)` — тип есть, значит интерфейс не пуст.

Идиома: не объявляйте переменную конкретного типа ошибки под
возврат. Возвращайте `nil` явно.

```go
func validate(c Course) error {
	if c.title == "" {
		return &ValidationError{Field: "title"}
	}
	return nil
}
```

Это единственное место в блоке A, где ошибка не ловится ни
компилятором, ни `go vet`, ни тестом на счастливый путь. Ловится
она только тестом, который проверяет отсутствие ошибки.

## Ветвление по типу

Последний остаточный рефлекс — динамическая типизация. `isinstance`
переезжает буквально:

```go
func describe(v any) string {
	switch x := v.(type) {
	case Course:
		return x.title
	case Student:
		return x.name
	}
	return "неизвестно"
}
```

Работает. Но каждый новый тип требует правки этой функции, а
компилятор о забытой ветке не скажет — вернётся строка про
неизвестное.

Идиома: если типы должны уметь одно и то же, это интерфейс, а не
`switch`.

```go
type Named interface{ Name() string }
```

`type switch` остаётся законным инструментом — для разбора ошибок,
для декодирования внешних данных, для случаев, где типы вам не
принадлежат. Но если ветвление идёт по вашим собственным типам,
это почти всегда признак, что контракт не выделен.

## See in real code

`io.Writer` — один метод, на котором держится вся работа с
выводом: файлы, сеть, буферы, сжатие. Хороший объект для
наблюдения: посмотрите, сколько несвязанных пакетов реализуют его,
ни разу не упомянув.

`error` — интерфейс с одним методом, объявленный в языке. Его
устройство объясняет ловушку с nil лучше любого описания.

## Упражнение

В пакете `lms` есть хранилище курсов и отчёт по ним.

```go
type Repository interface {
	Save(c Course) error
	Load(id int) (Course, error)
	Delete(id int) error
	Close() error
}

type memoryRepo struct{ courses map[int]Course }

func NewRepository() Repository {
	return &memoryRepo{courses: map[int]Course{}}
}

type NotFoundError struct{ ID int }

func (e *NotFoundError) Error() string { ... }

func (r *memoryRepo) Load(id int) (Course, error) {
	var e *NotFoundError
	c, ok := r.courses[id]
	if !ok {
		e = &NotFoundError{ID: id}
	}
	return c, e
}
```

Задание:

1. Напишите функцию `Render`, которой нужен только `Load`.
   Объявите для неё интерфейс так, чтобы пакет с отчётом не
   зависел от пакета с хранилищем.
2. Напишите тест на успешную загрузку, проверяющий, что ошибка
   равна `nil`. Убедитесь, что он падает, и объясните вывод.
3. Почините `Load`, не меняя тип `NotFoundError`.
4. Измените `NewRepository` так, чтобы `Close` стал доступен
   вызывающему. Проверьте, что `Render` при этом не потребовал
   правок — и объясните, почему.
5. Замените мок-хранилище в тесте на тип, объявленный прямо в
   тестовом файле. Сколько методов ему понадобилось?

Пятый пункт — проверка на то, усвоено ли главное. Если методов
получилось больше одного, вернитесь к первому.
